# EXP-810 — Batched decode is structurally unavailable on moe-infinity (engine API bug)

**Question.** exp809 measured a fixed 3,008-op/token dispatch tax (24 µs/op ≈ 72 ms/tok). Is that op stream batch-invariant — i.e., can batching amortize the orchestration tax (wall ms/token at B1 vs B2 vs B4)?

**Method.** TorchDispatchMode census (exp809 attempt-4 pattern) around left-padded batched `generate()` via `apply_chat_template(padding=True)`: arms WARM_B2(8 tok), B1/B2/B4/B2REP(128 tok), 8 prompts, OLMoE-1B-7B on RTX 6000 Ada. Gates: P1 ops/token within 1% across B1/B4; G1 wall(B4) ≤ 85% of B1; S1 B2≈B2REP; S2 rc=0 + wall sanity band. Preregistered fallback: if batched decode fails structurally, adjudicate BATCHING-UNAVAILABLE; P1/G1 N/A(engine); S2 records the failure verbatim.

**Result: BATCHING-UNAVAILABLE (engine).** All 5 arms × 2 attempts crashed at the identical site before producing a single token:

```
modeling_olmoe.py:102  freqs = position_ids[..., None].float() * self.inv_freq...
RuntimeError: Expected all tensors to be on the same device, but found at least two devices, cuda:0 and cpu!
```

- Attempt-2 (no explicit position_ids): 5/5 rc=1.
- Attempt-3 (explicit CUDA-resident `position_ids = mask.cumsum(-1)-1`): 5/5 rc=1, same site — the engine's `generate()` wrapper re-derives position_ids on CPU regardless of caller input.
- Trigger isolated: passing `attention_mask`/`position_ids` at all breaks the path — **B1 (batch=1) crashes whenever a mask is passed**, while exp809's bare-`ids` calls ran clean to completion. Batch size is not the cause; kwargs handling is.

**Adjudication (preregistered fallback).**
- P1 ops/token batch-invariance: **N/A(engine)** — no batched tokens ever produced.
- G1 amortization ≥15%: **N/A(engine)**.
- S1 replication: N/A — no data.
- S2: **FAIL recorded verbatim** — 5/5 arms rc=1 both attempts, crash site replicated from frozen `.out` artifacts.

**Findings.**
1. **Batched decode cannot run on the current moe-infinity stack** (torch 2.11.0+cu128, editable upstream tree at `be6e17b`-lineage engine): the `MoE.generate()` wrapper mishandles `attention_mask`/`position_ids`, leaving position embeddings on CPU. This is an upstream-actionable bug, not a harness error — two independent call shapes failed identically.
2. **Practical consequence for the op tax**: the 3,008-op/token × 24 µs orchestration burn (exp809) **cannot be amortized by batching today**. The mitigation path on this engine is op-stream reduction (fuse/batch dispatch internally — e.g. collapse the 1,191 detaches/token), not client-side batching.
3. The crash is cheap to reproduce (any masked generate) and cheap to characterize — a concrete upstream fix candidate: keep position_ids/mask on the input device through the wrapper's forward plumbing.

**Mechanics.** Attempt-1 VOID (tokenizer called on raw dicts instead of `apply_chat_template`; no artifacts). Attempt-2 VOID (engine device bug above). Attempt-3 VOID (explicit position_ids did not bypass the wrapper's re-derivation). All three preregistered/logged before adjudication; counting harness itself was smoke-verified on CPU (exp810 attempt-1 fix + exp809 attempt-4 lineage).

**Lineage.** exp809 (3,008 ops/tok tax) → **exp810 (batching unavailable on engine → tax not amortizable client-side; upstream bug isolated)**.
