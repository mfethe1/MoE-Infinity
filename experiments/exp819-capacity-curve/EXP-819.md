# EXP-819 — device_memory_ratio capacity curve (RAM↔latency tradeoff)

**Question.** How much latency does each unit of resident expert-cache capacity buy? Sweep `device_memory_ratio` ∈ {0.25, 0.35, 0.50, 0.65} × 3 reps (rotated orders asc/desc/alt), OLMoE-1B-7B through moe-infinity generate, un-instrumented truth standard (wall + token lists only), min-estimator, block-until-quiet gates (load <2.0, GPUs idle) before every arm.

**Preregistered gates.** G1_slope_positive (min wall monotone non-increasing in ratio) · G2_capacity_wins_ge10 (0.25→0.65 saves ≥10 ms/tok) · S2_min_replicated_10pct (2nd-min ≤ 1.10×min per condition).

**Verdict: hypothesis REFUTED — the curve is U-shaped with a clear optimum at 0.50, and peak GPU allocation is flat across all ratios.**

## Numbers (all re-derived from raw per-arm artifacts by verify819.py; extractor cross-check identical)

Min wall ms/tok (3 reps, sorted):

| ratio | reps | min | peak GPU MB |
|---|---|---|---|
| 0.25 | 95.7 / 107.4 / 107.8 | **95.7** | 4928 |
| 0.35 | 89.4 / 99.6 / 100.6 | **89.4** | 4928 |
| 0.50 | 79.9 / 82.1 / 86.2 | **79.9** | 4928 |
| 0.65 | 89.9 / 90.9 / 106.1 | **89.9** | 4928 |

- **G1 FAIL** (non-monotone): 0.25→0.35→0.50 improves (95.7→89.4→79.9), then 0.65 regresses to 89.9.
- **G2 FAIL**: 0.25→0.65 saves only 5.8 ms/tok (<10), and the wrong direction at the top: 0.65 is 12.5% slower than 0.50.
- **S2 FAIL (marginal)**: 0.25 = 1.1223×, 0.35 = 1.1141× (thrash variance); 0.50 = 1.0275×, 0.65 = 1.0111× (tight).
- Every 0.50 rep beats every 0.25/0.35/0.65 rep (worst 0.50 rep 86.2 < best non-0.50 rep 89.4) — dominance holds under min-estimator, so the optimum is not an estimator artifact.
- 0.25 is 19.8% slower than 0.50; 0.65 is 12.5% slower than 0.50 (script-derived).

## Finding

`device_memory_ratio` does **not** change peak GPU allocation in this configuration (4928 MB at every ratio — the model weights dominate VRAM; the ratio tunes the expert-cache policy within that footprint). Because the memory cost is flat, the ratio is a **free performance knob**, and 0.50 is its measured optimum: too small a cache thrashes fetch-wait (0.25/0.35, also the high-variance conditions), and 0.65 is past the working-set sweet spot without buying residency in measured VRAM. **Deploy guidance: `device_memory_ratio=0.50`.** Same envelope, 19.8% faster than 0.25.

**Infra notes.** Two clean gate aborts (900s budget) during a ~2h CI build wave on Winnie (loads 20–35); attempt-3 extended the gate budget to 3600s (blocking precondition only — no formulas, estimator or arm protocol changed; extractor block byte-identical to the registered run819.sh). All 12 measured arms ran in quiet windows (load <2.0) with rc=0.
