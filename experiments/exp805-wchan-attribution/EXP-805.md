# EXP-805 — The main thread is not sleeping: 79.5% of decode it is RUNNING (CPU spin-burn)

**Question.** exp803 (#120): the attention bucket is 98.4% orchestration, not math;
graphs don't help. exp804 (#121): only 6.2% of the gap blocks in Python-visible
sites. WHERE does the main thread actually sit during decode — which kernel wait
channel owns it?

**Method.** Standard decode battery (exp802/804 envelope: OLMoE-1B-7B bf16, ratio
0.50, MOE_GROUPED_DECODE=1, threads 4, GPU1, 8 prompts, pre/full phases, bucket hooks
for PT_attn replication). No patches, no binary swap. External stdlib sampler polled
`/proc/<pid>/task/*/stat` + `/wchan` every 50 ms (17–19 effective samples/s/thread)
until the probe's `full-end` marker. Main thread = tid == pid. Arms: WARM_8,
BASE_A_32, BASE_B_128, BASE_B2_128. 4/4 rc=0, 0 flagged. Seal `aa0127e5…3c25`.

**Mechanics note (honest).** Frozen extract805.py assumed per-arm phase markers, but
the runner recreates phases.log per arm, so only the last arm's markers survived →
crash. Verified root cause, then repair extractor `extract805b.py` (sha `24a750ea…`):
reconstructs each arm's full-phase window deterministically from that arm's cell JSON

**Results (BASE_B_128, replicate BASE_B2_128 in parens).**
- **P1 PASS, but the answer is not a wait channel:** main thread state R / wchan 0
  (running, not sleeping) on **79.5% (79.3%)** of full-phase samples.
  `futex_wait_queue` S: 17.2% (17.5%). Everything else < 2%.
- **S1 PASS:** 1,752 main-thread samples at 17.6/s. **S2 PASS:** PT_attn replication
  125.2 / 124.1 ms/tok ∈ [110,150]; 0 flagged. Worker threads: parked in
  `futex_wait_queue` (~69–72k samples), CUDA thread `cuda00002000009` in
  `do_sys_poll`.
- Lineage: decode wall 98.0 ms/tok ≈ exp804 BASE_B's 100.3 (warm envelope; exp802's
  737 ms/tok figure was the cold/first-battery condition).
- G1 mapping: top "channel" = RUNNING → mechanism label **spin-burn / native CPU
  work**, i.e., the main thread spends the attention bucket executing native code,
  not blocked.

**Interpretation.** The three-step decomposition now reads: attention bucket
~125 ms/tok = 1.98 ms GPU math (#120) + ~0.2 ms launch (#120) + ~7.9 ms Python D2H
(#121) + **~100+ ms main-thread CPU execution invisible to Python** — of which at
most 17% is futex sleeping (#805). Candidate mechanisms: CUDA driver spin-wait
(`cudaDeviceScheduleAuto` picks spin on this 1-GPU/12-CPU box — every implicit sync
inside the dbuf fetch path burns a core), and/or native C++ bookkeeping (routing
tables, buffer management) on the decode critical path. Worker GEMM threads being
core-starved by the spinning main thread is a live wall-time suspect.

**Routing.** exp806: controlled A/B of `cudaSetDeviceFlags(cudaDeviceScheduleBlockingSync)`
via ctypes before context init (no new installs, no binary swap) + per-thread CPU
accounting (`/proc/*/task/*/stat` utime deltas pre/full). Preregistered: P1 main-thread
CPU ms/tok drops ≥5×; G1 decode wall ≤ 1.05× baseline (spin-release must not cost
wall); S-gates on sampler coverage and PT_attn band. If wall improves materially,
spin-burn was starving the expert GEMM workers → direct perf lever; either way the
spin diagnosis is confirmed or refuted by the CPU-time collapse.
