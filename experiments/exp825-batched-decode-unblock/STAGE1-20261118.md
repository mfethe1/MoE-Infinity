# EXP-825 Stage 1 — crash isolated, minimal fix validated (2026-11-18)

Three probes on Winnie GPU 1 (RTX 4080-class), model OLMoE-1B-7B-0125-Instruct,
offload dir `~/moe-offload-olmoe-0125-r05`, config `device_memory_ratio 0.50, lcnu,
num_threads 4, gpu_only_expert_routing, adaptive_resident_mode legacy, no prefetch`.
All numbers below are verbatim from the probes' RESULT_JSON lines; scripts archived
alongside this report (shas in commit).

## S1a — s0p_probe.py (sha fe242718…): crash is loop-level, not kwargs-level

| arm | batch | caller kwargs | result |
|---|---|---|---|
| PD | 1 | none | OK |
| PC | 1 | mask+pos (CUDA) | OK |
| PB | 2 | none | CRASH `cuda:0 and cpu` |
| PA | 2 | mask+pos (CUDA) | CRASH `cuda:0 and cpu` |

- Batch-1 + explicit CUDA mask/pos does NOT crash → exp810's retracted receipt line
  is now disproven by direct test (it had never run; the claim is also false).
- Batch-2 crashes with BARE ids → the error is independent of caller kwargs.
  Any batch≥2 call takes the HF passthrough (`big_modeling.py:1340`) and dies in the
  rotary matmul. Mythos Change A (align caller kwargs) is a no-op; Change B (native-path
  mask guard) is irrelevant — the native path never crashes.

## S1b — s0p2_identify.py (sha 84a8c310…): the CPU tensor is HF-loop position_ids

Rotary-forward shim logged every call's devices:
- Batch-1 (PD, 8 calls): x cuda:0, position_ids cuda:0, inv_freq cuda:0 — clean.
- Batch-2 prefill (the crash call): x cuda:0 [2,16,2048], inv_freq cuda:0,
  **position_ids cpu [2,16]**.
- `hf_first_param_device: cpu`, `rotary_inv_freq_device_at_rest: cpu` — the HF model's
  dense params (and rotary buffer at rest) live on CPU after offload; the engine moves
  inv_freq to GPU during decode, but HF's generate loop derives position_ids/cache_position
  from the model's device (= CPU) and **discards the caller's CUDA position_ids** — the
  second silent discard, sibling of the native-path mask drop (Mythos P4).

## S1c — s0p3_fixprobe.py (sha e32e7377…): 2-line guard unblocks batched decode

Monkeypatched `OlmoeRotaryEmbedding.forward` guard: if `position_ids.device != x.device`,
move it. Results: warm b1 OK; **F_b2_bare OK** (was CRASH); **F_b4_bare OK**;
`rotary_calls 16, realigned 16` — the guard realigned at EVERY call (prefill and each
decode step), so per-step CPU derivation is persistent, not a prefill-only event.

## Minimal fix (validated)

In the model file's `OlmoeRotaryEmbedding.forward` (modeling_olmoe.py):

```python
if position_ids.device != x.device:
    position_ids = position_ids.to(x.device)
```

Device-alignment guard, not caller-side plumbing; correct regardless of which side moves.
This is upstream-worthy for the model repo and engine-agnostic.
