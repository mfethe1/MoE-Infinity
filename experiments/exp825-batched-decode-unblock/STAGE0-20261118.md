## S0a — frame above HF in B>1 tracebacks
`big_modeling.py:1340` (`return self.model.generate(input_ids, **kwargs)`) — the HF
passthrough path (Mythos P3). Identical in all five `.out` files (B2, B4, WARM_B2, B2REP,
and B1). No `:854` (`_native_model_forward`) frame anywhere.

## S0b — the B1 arm never ran
Every traceback's outermost harness frame is `batch-B1_128.py:67` — the **shared warmup**
`batch_gen(["Say hello.", "Say hi."], 8)`, a batch-2 call. All five arms died in the same
warmup before any arm-specific tagged call executed (arm calls are lines 71+).

**RETRACTION:** exp810's receipt line "batch 1 crashes when attention_mask is passed" is a
mislabel — the warmup (batch 2, explicit mask+pos) crashed; batch-1-with-mask was never
tested. Mythos H4's "contradiction" was real and is now resolved in the opposite direction:
there is NO evidence that the native path mishandles explicit kwargs, because no call ever
reached it.

## S0c — harness device facts
`batch-*.py` lines 57–61: `ids`, `mask`, AND `pos` are each `.to("cuda:0")` before
`generate(ids, attention_mask=mask, position_ids=pos, ...)`. Left padding, `min=max`
tokens, `device_memory_ratio 0.50`, `lcnu`, `MOE_GROUPED_DECODE=1` +
`MOE_INFINITY_UNVALIDATED_HW=1`.

**Consequence — Mythos H1's device premise is refuted:** the caller-side mask and
position_ids were already on the GPU, yet the crash still reports `cuda:0 and cpu` at
`modeling_olmoe.py:102` (rotary matmul `inv_freq_expanded @ position_ids_expanded`).
The CPU tensor is therefore NOT a caller kwarg; it is engine- or HF-internal:
- H-a: rotary `inv_freq` buffer left on CPU (per-module hook missed it / registered after)
- H-b: HF `_prefill` re-derives `cache_position`/`position_ids` on CPU (dense params live
  on CPU per boot log, so `model.device` may report CPU and `torch.arange` lands on CPU)
- H-c: both.

Mythos's Change A (align caller kwargs to the embedding device) is a **no-op for this
crash** — caller kwargs are already on the GPU. The fix must target whichever tensor is
actually on CPU; stage 1 must discriminate first.

## Env-var confound ruled out (Q4 partial)
`MOE_GROUPED_DECODE=1` and `MOE_INFINITY_UNVALIDATED_HW=1` are set in the WORKING lineage
too (`exp821/p11_run.sh:12-13,69`; `exp824/p14_batt.sh:14-15,72`) — not a discriminator
between crash and working runs. The working lineage calls `generate(ids)` bare, batch 1
(native path P4–P7); the crashing calls pass explicit kwargs and/or batch ≥ 2 (HF path).

## Stage-1-lite discriminator (queued, GPU 1, AFTER exp824 seals)
`s0p_probe.py` — one process, four tiny calls, each try/except-wrapped, order
PD→PC→PB→PA so the known-good arms run before the expected crash:
- PD: batch-1 bare ids (control, known good)
- PC: batch-1 + explicit CUDA mask/pos (tests the retracted receipt claim properly)
- PB: batch-2 bare ids (**the key discriminator**: HF path without explicit kwargs —
  crash means loop-level CPU tensor (H-b), clean means kwargs-path)
- PA: batch-2 + explicit CUDA mask/pos (expected: reproduces the exp810 crash)
Plus `inv_freq.device` inspection of every rotary module before/between/after arms and the
HF inner model's first-parameter device. Read-out: identifies the CPU tensor by direct
observation, which selects the actual minimal fix.
