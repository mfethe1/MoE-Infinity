# EXP-808: The userspace burn is DISTRIBUTED per-op orchestration — no single hot function

**Date:** 2026-11-13 · **P1 FAIL (decisive answer) — G1 FAIL — S1 PASS — S2 PASS**
**Lineage:** exp805 (RUNNING 79.5%) → exp806 (not driver spin) → exp807 (userspace 72.1 vs

## Question

Which function owns the main thread's ~72 ms/tok userspace burn? PC-sample RIP at 20 Hz
via ptrace (no profiler tools exist on this box), symbolize offline against
`/proc/<pid>/maps` + ELF `.symtab` of the mapped libraries.

## Method

probe808 = standard battery + `prctl(PR_SET_PTRACER_ANY)`. pcsamp808: `PTRACE_SEIZE` +
`PTRACE_INTERRUPT → waitpid → GETREGS → CONT` @20 Hz on the main tid during the `full`
phase. 3 arms, 3/3 rc=0, sampler events=[]; 1944/1980 samples per BASE cell.
Offline symbolizer: minimal ELF64 `.symtab` (STT_FUNC) reader for `_engine`,
`libtorch_cpu/cuda`, `libcuda`, `libmoe*`, module bucketing otherwise.

**Mechanics repair (extract808b, sha16 9c4708a8):** the prereg classifier read
`/proc` state == 'R'; under ptrace-stop every sample reads state 't' (verified: 100% 't'
in all three frozen JSONLs) → R-filter structurally empty. Correct discriminator, frozen
in the data all along: **`orig_rax == -1`** = interrupted executing userspace code.
Gates/constants unchanged. Bonus: `orig_rax != -1` gives the syscall census exp807 lost
to Yama EPERM.

## Results (BASE_B_128 / BASE_B2_128; userspace_n 1238/1255 of 1944/1980)

**Syscall census (all samples): USERSPACE 63.6% · futex 18.9% · ioctl 17.3% · write 0.6%** —
the exp807 census, recovered. (G1's ≤0.30 in-syscall was a PURE-USERSPACE confirmation
side-gate; measured 0.363 sample-share — time-share from utime/stime clocks was 0.17.)

**Userspace PC histogram by module (share of userspace samples, replicated ±1 pt):**

| module | share | what it is |
|---|---|---|
| python3.12 | **44.7%** | CPython interpreter opcodes/refcounting between ops |
| libcuda.so | 14.4% | CUDA driver entry (launch/sync paths) |
| libtorch_cpu | 11.1% | aten: TensorIterator compute_shape/build, empty_generic allocs |
| libc.so | 6.6% | allocator/memcpy |

Top single symbol: `at::TensorIteratorBase::compute_shape` 5/1238 = **0.4%** (B2:
`torch_function_mode_enabled` 7/1255 = 0.56%). P1 (≥30%) and G1 (top-3 ≥50%) FAIL —
**the answer**: there is NO single hot function. The ~72 ms/tok userspace burn is
thousands of small per-token operations each paying Python-interpreter + torch
dispatcher + iterator-build + allocation + pybind + driver-entry overhead.
S1 PASS (walls 92.3/94.0 in band); S2 PASS (PT_attn 121.8/127.8).

## Interpretation

This closes the attribution chain: the offload pipeline's main-thread cost is not a
bug in one place — it is **eager per-op orchestration tax** (CPython ≈ 45% of userspace
PCs, torch dispatch/iterator/alloc ≈ 25%, driver entry ≈ 14%). exp804's "Python 6.2%"
measured Python-visible *CUDA-event sites*; PC sampling shows the interpreter binary
itself dominates userspace time between kernel launches. The 84 minflt/token (exp807)
= per-op tensor allocations; the fix class is op-count collapse: CUDA Graphs /
torch.compile(reduce-overhead) on the decode path, not micro-optimizing any function.
