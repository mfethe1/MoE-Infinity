# EXP-806: The main-thread burn is NATIVE COMPUTE — blocking-sync does not touch it

**Date:** 2026-11-13 · **Verdict: P1 FAIL (refutes driver spin-wait) — G1 PASS — S1 PASS — S2 PASS**
**Lineage:** extends exp805 (#122: main thread RUNNING 79.5% ≈ spin-burn hypothesis).

## Question

exp805 found the decode main thread executing (state R) 79.5% of the phase. Leading
hypothesis: CUDA runtime spin-wait sync (`cudaDeviceScheduleAuto` spins on a quiet box).
Test: set `cudaDeviceScheduleBlockingSync` via ctypes **before** CUDA context creation;
if the burn is driver spin, main-thread CPU should collapse ≥5× without hurting wall.

## Method

probe806.py = exp805 harness (identical envelope, hooks, walls) + per-thread CPU
accounting (utime+stime deltas at phase marks, CLK_TCK=100) + `--blocking-sync`
(ctypes `cudaSetDeviceFlags(0x04)`, rc logged; applied before any context creation).
Per-arm phase/pid files (fixes exp805's clobber bug). Sampler per arm (corroboration).
Arms: WARM_8, BASE_B_128 ×2, BS_B_128 ×2. No binary swap, no monkeypatch. 5/5 rc=0.

| worker CPU ms/tok | 67.7 | 67.0 | 0.99 |
| main R-share (sampler) | 0.815/0.818 | 0.812/0.822 | — |
| PT_attn(128) ms/tok | 131.5/129.2 | 122.9/125.6 | — |

- **S1 PASS:** `cudaSetDeviceFlags` rc=0 in both BS arms — flag genuinely applied.
- **P1 FAIL (the result):** main-thread CPU did NOT collapse (0.973 vs gate ≤0.20).
  The ~87 ms/tok of main-thread CPU is real work executed in native code, not the
  driver's sync policy. Blocking-sync is cheap and slightly wall-positive (−2.4%,
  within noise band), but it is not the lever.
- **G1 PASS** (0.976 ≤ 1.05). **S2 PASS:** PT_attn ∈ [122.9, 131.5] ⊂ [110,150];
  flagged 2/5 (both POST-loadavg self-decay after clean PRE gates — WARM POST l1=3.48
  read seconds after probe exit; recorded, not discarded; within the 0–2 band).
- Worker CPU and R-share unchanged → no hidden starvation relief either.

## Interpretation

The decode-critical-path decomposition now reads:
**~125 ms/tok PT_attn = 1.98 GPU math + ~0.2 launch + ~7.9 Python-visible D2H
+ ~87 main-thread NATIVE COMPUTE (MoE-Infinity C++ offload pipeline: expert
scheduling/routing, prefetch decisions, buffer management) + ~17% futex-wait slices.**
Driver spin is eliminated as the primary mechanism (blocking-sync applied, verified,
no effect). The CPU burn is the cost of the runtime's own orchestration algorithm —
the same conclusion direction as exp803 (98.4% orchestration), now attributed to
native code paths rather than waiting.

## Mechanics notes (honest)

- Runner `flagged` counter counts POST-arm gate FAILs; POST loadavg is read seconds

  recorded in running.json BEFORE any BASE/BS results existed; in the event the count
  (2) fell inside the preregistered 0–2 band, so no repair was applied.
