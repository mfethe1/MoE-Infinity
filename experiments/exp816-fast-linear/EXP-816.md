**Adjudication.**
1. **The intervention is behaviorally clean** (S1 PASS — same `addmm` accumulate path as `F.linear`; FAST self 0.556 ≥ HOOK self 0.526): a safe optimization that simply doesn't pay.
2. **Wall-neutral despite −65.5 ops/tok**: the removed `t` dispatches are view metadata (no kernel), the GEMM is cuBLAS-bound and unchanged. Remaining 19.75% of `t` ops belong to moe-infinity's custom ExpertLinear (not `nn.Linear`) — explains the P1 structural miss.
3. **Belief update (key lesson of the series):** once the hook storm (exp812) was fixed, dispatch COUNT stopped predicting wall. Wall owners are memory-movement ops — RMSNorm's fp32 upcast/downcast + scale muls were real bandwidth work (exp814/815: −13.5/−10.2 ms/tok); decomposition views and GEMM plumbing are free at these sizes. The exp813 "16% linear / 8% rope" attributions are *op shares*, not *time shares* — rope (8%) is now deprioritized as wall-irrelevant by the same logic.
4. **What's left for wall:** the ~1,758 residual ops/tok are ~97% orchestration cheap-per-op + the true compute (GEMM + attention + expert fetch). Further wall gains must target data movement (offload fetch path, exp794's 43.7-pt fetch-wait) or fused compute (exp814-class), not dispatch hygiene. Fast-Linear is kept as a verified-safe optional patch (S1-proven) but not adopted (no pay).

**Lineage.** exp813 (residual attribution) → exp814/815 (RMSNorm fusion: wall owners = memory movement) → **exp816 (Linear decomposition: dispatch hygiene, wall-neutral — closes the op-share ≠ time-share question)**.
