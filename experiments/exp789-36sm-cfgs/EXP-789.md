## Question

exp787's launch-config sweep was restricted to the 8 RTX-PRO-6000-tuned instantiations.
Do NEW (MT,WR,WK,U) shapes designed for 36 SMs beat the shipped default table on
consumer sm_120 for batch-1 decode?

## Design

Four uniform-config instantiations added to `GMOE_PRO6000_CONFIGS` (additive; the env
override `MOE_GROUPED_MOE_CFG` selects them):

| Arm | (mt,wr,wk,u) gate_up;down | 36-SM hypothesis |
|---|---|---|
| N1 | 1,4,2,2 | mid split — 2x CTAs vs (1,8,1) |
| N2 | 1,2,8,2 | wide WK smem-reuse ILP, 512 threads |
| N3 | 1,4,1,4 | row-split only, unroll 4 |
| N4 | 1,1,4,4 | narrow CTA, wide unroll |

C = shipped default table (no override). Decision rule declared pre-probe: promote to
frozen 24-prompt confirmatory iff pooled mean decode tok/s >= +2% vs C.

## Results (8 prompts, n=8/arm)

| Arm | tok/s | delta vs C |
|---|---|---|
| C default | 11.569 | — |
| N1 1,4,2,2 | 11.675 | +0.91% |
| N2 1,2,8,2 | 11.611 | +0.36% |
| N3 1,4,1,4 | 11.694 | **+1.08%** |
| N4 1,1,4,4 | 11.643 | +0.64% |

## Conclusion

**NO-MOVE.** All four 36-SM shapes land within +1.1% — below the +2% gate. The shipped
PRO-6000-tuned table is near-optimal for this workload even outside its own 8 shapes,
so launch geometry is not the remaining decode bottleneck on consumer sm_120; that is
consistent with exp786/exp787's residual (~82% of decode time outside the grouped
kernels). Determinism thread remains parked (exp788 refuted the epilogue lever); next
frontier is the non-grouped residual (attention/prefill path) or ratio-policy work.
The 4 added instantiations stay in the tree harmlessly (compile-time only) for any
future mixed-config search.
